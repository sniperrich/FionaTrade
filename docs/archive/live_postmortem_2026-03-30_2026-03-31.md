## 4. 关键结构性结论

### 4.1 这不是盘后乱交易

- `3/31` 的真实订单都发生在 `market_open`
- 收盘前风控明确执行了 `FLATTEN`
- 亏损主要来自已有仓位的价格重估，而不是盘后继续新建仓

### 4.2 live 现在不是“严格 news-led”

虽然设计权重是 `news 60 / tech 20 / macro 10 / fund 10`，但在真实投票和风控链路里：

- `news_signal = BUY` 的票，仍然可能因为其他模块一致看空而被做空
- 结果就是：系统会在“个股新闻偏多”的情况下，仍做出股票级别的空单

### 4.3 live 执行缺少事件硬锚点

`2026-03-30` 之后的 `submitted` 真实订单：

- 总数：`16`
- `trigger_event_id is null`：`16`
- `linked_trigger_event`：`0`

这说明：

- 你现在的 live 单不是通过“结构化事件 -> 证据链 -> 下单”打通的
- 而更像“基于新闻聚合上下文让 agent 出动作”
- 这对回溯、过滤、源质量控制都不利

## 5. 建议优先级

### P0

- live 启动后增加 warm-up，禁止直接吃启动前积压新闻开仓
- `submitted` 交易必须要求 `trigger_event_id`
- 默认收紧 live 来源到高质量白名单：`benzinga,reuters,cnbc,earnings_release,sec`

### P1

- 当 `news_signal = BUY` 但最终准备 `SHORT` 时，默认降级为 `HOLD`
- 除非存在 tier0/tier1 双确认，或者同主题 multi-source corroboration
- 首轮 live cycle 限制最大新仓数，例如前 30 分钟最多 `2` 笔

### P2

- 把 broker 侧 bracket fill 真正回写到 `live_trades`
- 否则 live 复盘只能得到近似 mark-to-close，拿不到完整 realized attribution

---

## 6. 当前结论一句话版

- `3/30`：赚钱，但方式是“用大量新闻积压快速堆出高集中度空头篮子”，不可持续  
- `3/31`：这批空头在隔夜和次日盘中被反向行情打穿，形成约 `-1648` 的单日损失  
- 真正该修的不是收盘前是否平仓，而是 live 执行前的事件锚点、来源过滤、首轮建仓节奏和 news-vs-macro 的冲突处理
